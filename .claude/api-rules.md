# API・バックエンド系リポジトリの規約（api-rules）

> **⚠️ このリポジトリが外部 API・DB・認証のいずれも持たない場合、以下のルールは適用対象外（無視してよい）。** 該当の有無は実コード（`app/api/`・DB・認証の利用）で判断する。
>
> **⚠️ このファイルは dev-commons が正典として管理し、sync-standards ワークフローが全リポジトリへ PR で配布する（全リポに配布し、API・DB・認証を伴うリポジトリでのみ適用する）。各リポジトリで直接編集しない（次回同期で上書きされる）。**
> 変更するときは dev-commons の `sync/.claude/api-rules.md` を編集する。
>
> このファイルは **外部 API・DB・認証を伴うバックエンド系リポジトリに効く共通規約**。ルートの `CLAUDE.md` が常に import し、上記ガードにより該当しないリポジトリでは適用対象外となる。
> API ドキュメント・カバレッジ観点は「見せ方・契約」の規約（＝ outcome の形）を書く。実装方式（スキーマから spec を生成する手段など）は各リポジトリの product code の領分であり、ここには書かない。

## API リファレンスの提供（OpenAPI + リファレンス UI）

- **OpenAPI 3.1 を配信する**。実行時にエンドポイントで配信することを推奨し、`version` は `package.json`、`servers` はアクセス元 origin を反映する（固定値をドキュメントに焼き込まない＝ source of truth 原則）。
- **API リファレンス UI を提供する**（Stoplight Elements 等）。配信中の OpenAPI を参照して描画する。
  - CDN で読み込む場合は**メジャーバージョンを固定**する（`latest` は破壊的変更・供給網リスクのため禁止）。
  - リファレンス UI は**認証の背後**に置く（公開 API でない限り未認証で仕様を晒さない）。
- **OpenAPI（配信 spec）を仕様の唯一の正とする**。手書きの spec を別に持たない。スキーマ定義はコード（例: 各リポジトリのスキーマ層）を正とし、そこから spec を導出する。

## API ドキュメントは配信 spec に一本化する

API のドキュメントは**配信 spec ＋ リファレンス UI（Stoplight 等）に集約**する。別途 `docs/api.md` を設けない（内容が spec と二重化しドリフト源になるため）。人間向けのナラティブも spec に含める:

| 内容 | 置き場所（配信 spec 内） |
|------|-------------------------|
| 概要・意図 | `info.description`（Markdown） |
| 認証（方式・キー発行手順・保護対象） | `securitySchemes` ＋ `info.description` |
| 共通仕様・エラーレスポンスの形（例: `{ error }`）・サーバー起因の失敗（500） | 各操作の `responses` ＋ `info.description`（共有 `components/responses` にまとめてもよい） |
| エンドポイント一覧・request/response 定義 | `paths`（＝ リファレンス UI が描画。これが仕様の正） |
| クイックスタート（`curl` 等） | `info.description`（リファレンス UI の code sample 自動生成も活用） |

- **サーバー起因の失敗（500）も各操作の `responses` に宣言する。** 共通ラッパーが捕捉されない例外を 500 に変換する構成では**全操作が 500 を返しうる**ため、一部の操作だけに宣言しない。`info.description` の表に書くだけでは `paths` に現れず、リファレンス UI にも出ない。宣言漏れは「テストでは 500 を確認しているが spec には無い」という食い違いになり、**配信 spec を仕様の唯一の正とする原則が崩れる**（検査の形は「テスト」を参照）。
- **エラー応答を各操作にインラインで書くか共有 `components/responses` にまとめるかは問わない。** 文言が操作ごとに固有になる API では、グローバルな名前に寄せると名前が文脈を説明できなくなる。**どちらの方式でも、全エラー応答が共通のエラースキーマを指すことをテストで固定する**（下記「テスト」）。守るべきは構造ではなく契約である。
- README には配信 spec / リファレンス UI（`/openapi.json`・`/api-reference` 等）への**導線を1つ**置く。
- `info.description` に流し込む散文をリポジトリ内の Markdown に置いて spec ビルダーから読み込む形にしてもよい（実装詳細。ただし**独立した `docs/api.md` としては持たない**）。

## ドキュメント（API・バックエンド系）

該当する実装がある場合にのみ作成を必須とする（どれを持つかは `docs/` 配下の実在で判断する）。source of truth 原則に従い、各 doc は意図・契約・規約を扱う（コードが正の内容は書かない）。

| 条件 | ファイル | 必須セクション |
|------|---------|--------------|
| 外部 REST API を提供する | （`docs/api.md` は設けない） | 配信 OpenAPI spec ＋ リファレンス UI に一本化（上記「API ドキュメントは配信 spec に一本化する」参照） |
| Server Actions を採用する | `docs/actions.md` | Action 一覧、引数・戻り値・エラー定義、共通仕様 |

## セキュリティ（バックエンド）

DB・認証を伴う API リポジトリのセキュリティ規約（全 web アプリ共通の XSS 等は common-rules「セキュリティルール」を参照）。

- **ユーザーデータ分離**: DB アクセスは `where` に所有者の識別子（`userId` 等）を含めて絞り込む、または取得後に所有者を検証する。全 API ルート・書き込み経路でログイン済みユーザーの確認を行う
- **リクエストの識別子を信頼しない**: 操作対象ユーザーは常にサーバ側のセッション（認証情報）から取得する。リクエストパラメータの `userId` 等をそのまま使わない
- **SQL の安全な組み立て**: 生 SQL（`$queryRaw` / `$executeRaw` 等）を文字列連結・未サニタイズ入力で組み立てない。未検証の入力を `orderBy` / 動的キー / フィールド名にそのまま使わない
- **エラーレスポンスに内部情報を含めない**: サーバー起因の失敗（API ルートの 500、Server Actions の予期しない例外）をクライアントへ返すときは固定文言とし、例外メッセージ・接続先・スタック等をそのまま返さない
- **401 には `WWW-Authenticate` を付ける**: RFC 9110 は 401 応答に `WWW-Authenticate` ヘッダを含めることを求める。Bearer トークンなら `WWW-Authenticate: Bearer`（RFC 6750）。これが無いとクライアントは応答から認証方式を判断できない
  - `Basic` は使わない（ブラウザがネイティブの認証ダイアログを出す）。`Bearer` は出さないため CORS 対応の API でも安全
  - **CORS 対応の API では、ブラウザの JS からこのヘッダは既定で読めない。** 届ける必要があるなら `Access-Control-Expose-Headers` に加える（`curl` 等からは最初から見える）
  - トークンが無い場合は `Bearer` のみ。トークンが送られたが無効な場合に `Bearer error="invalid_token"` のような詳細を付けられるが、両者を区別するには認証関数が理由を返す必要がある。まず `Bearer` 固定で入れ、必要になってから区別する

## Server Actions の例外の扱い

> 本節は **Server Actions を採用するリポジトリ**にのみ適用する（採否は実コードで判断する）。

Next.js はエラーを 2 種類に分けて扱う方針を文書化している（同梱 docs の `01-app/01-getting-started/10-error-handling.md`）。これに従う。

| 種類 | 扱い |
|------|------|
| 業務エラー（バリデーション・一意制約違反など、呼び出し側が分岐できる失敗） | **戻り値でモデル化する**（`{ error }` を返す）。`try`/`catch` で捕まえて変換するのではなく、そもそも throw しない形にできるならそうする |
| 予期しない例外（DB 障害など、バグや障害を示すもの） | **再送出する。** エラーバウンダリ（`error.tsx`）が受け、クライアントには汎用文言と `digest` だけが渡り、`digest` でサーバー側のログと突き合わせられる |

- **予期しない例外を `{ error }` に変換するのは例外的な扱いとする。** 画面内にインラインで文言を出す必要がある場合に限り認めるが、その場合は**必ずサーバー側に記録する**（`console.error` 等）。変換すると `digest` による突き合わせが失われるため、記録が無いと障害の痕跡が完全に消える。
  ```ts
  // これは作らない（例外がどこにも残らない）
  } catch {
    return { error: "保存に失敗しました" };
  }
  ```
- **`redirect()` / `notFound()` を広い `catch` の中に置かない。** これらは例外として実装されているため、`catch` が制御フロー例外を飲み込む。try の中に入れる必要があるなら `unstable_rethrow` を使って再送出する。

> 本節は API ルート（`500 { error }` を返す共通ラッパー）とは別の契約。API ルート側は各リポジトリの `docs/architecture.md` が定義する「エラー分類の契約」に従う。

## 外部 API の操作ログ（監査ログ）

> 本節は**外部クライアントへ REST API を提供するリポジトリ**にのみ適用する（ファイル冒頭のガードのとおり）。ホスティング先・フレームワークに依存しない形で書き、依存する値は例として示す。

外部クライアントへ REST API を提供するリポジトリは、**誰のキーで・いつ・何を操作したか**を追えるようにする。プラットフォーム側のリクエストログはパス・ステータス・時刻のみでユーザーを特定できない。public リポジトリではエンドポイント・パラメータ構造が既知であり、異常アクセスの検知手段が無い状態は実リスクになる。

### 出力の形

**1 行 1 JSON で標準出力に書く。** 保存先（Log Drain / DB / 外部サービス）を後から変えてもルート側を触らずに移行できるようにするため。

```json
{"type":"audit","at":"2026-10-22T04:05:06.789Z","userId":"clxxxx","method":"PATCH","path":"/api/items/clyyyy","query":"?page=2","status":200,"ip":"203.0.113.1","bytes":145}
```

### 記録する / しない

**原則は「全リクエストを記録する」**。メソッドやステータスで肯定側を列挙すると、列挙から漏れた形が無記録になる。除外は下表に限る。

| 対象 | 記録 | 理由 |
|------|------|------|
| **メソッド・ステータスを問わず全リクエスト** | **する** | 漏洩キーによるデータの列挙・持ち出しは GET で行われ、ID の当てずっぽう（IDOR 探索）は登録済みパスの 404 として現れる。書き込みや特定ステータスだけでは痕跡が残らず、導入目的を取りこぼす |
| 401 / 403 | する（上記に含む） | 総当たり・権限外アクセスの検知。`userId` が取れない場合は接続元 IP で追う |
| 未登録パスへのアクセス | する（上記に含む） | エンドポイント列挙の痕跡。**メソッドを問わない**（`OPTIONS /api/<推測パス>` も列挙に使える） |
| **登録済みパス**への CORS プリフライト（`OPTIONS` → 204） | しない | 操作ではなく、登録済みパスなら常に 204 を返すだけで何も明かさない。**未登録パスへの `OPTIONS` は上記のとおり記録する** |
| 画面操作（Server Actions / Server Components） | しない | 本契約の対象は外部 REST API のみ |

- **APIキーは記録しない**（ハッシュ・prefix も含めない。`userId` で足りる）。記録すると**ログの保存先がキーの保管場所になる**
- **リクエスト/レスポンスボディは記録しない**
- **接続元 IP は、ホスティング先が保証する取得元から取る。** 401 では `userId` が取れないため IP が唯一の識別子になる。`X-Forwarded-For` の先頭要素を使うのは、**ホスティング先がこのヘッダを上書きする場合に限る**（例: Vercel）。追記する構成では先頭要素は**クライアントが自由に指定できる**ため、攻撃者の指定した IP を記録することになり総当たり検知が成立しない。自分のホスティング先がどちらかを確認する
- クエリ文字列はそのまま残す（列挙の検知に効く）。**この契約が崩れるため、秘密情報をクエリで受け取ってはならない**（APIキーに限らず、招待・共有・リセット等のトークンも含む。受け取るとログの保存先が秘密の保管場所になる）
- 本文のバイト数（`content-length`）は残してよい。内容を持たずにバッチ更新の規模が分かる。**ただし RFC 9110 どおり 10 進数字列のみを受ける**（`Number()` を使うと `""` が 0、`"1e3"` が 1000、`"0x10"` が 16 になり、クライアントが送った不正な値から数値をでっち上げる）

### 記録箇所

**各ルートに記録処理を散らさない。** 全ハンドラを包む共通ラッパーに置く。捕捉されない例外を `500 { error }` に変換するラッパー（各リポジトリの `docs/architecture.md` が「エラー分類の契約」として定義する）と同じものを使う。

ラッパーは認証ユーザーを知らない（解決は各ハンドラ内の認証関数）ため、両者をつなぐ仕組みが必要になる。**手段は各リポジトリの product code の領分**とし、ここでは満たすべき条件のみ規定する。

- **`userId` は「有効なユーザーか」の判定より前に記録する**。無効化済みユーザーの未失効キーが使われた場合、サーバーは「誰のキーか」を知っている。401 を返すとしてもそれを記録しないと、**退職者の漏洩キーと当てずっぽうの総当たりがログ上で区別できない**
- **ミドルウェア層が自分で応答を返す経路**（未登録パスの 404 等）も記録する。ここが抜けるとエンドポイント列挙が無痕跡になる
  - 記録するのは**ミドルウェアが応答を返す場合に限る**。後続へ通す場合は最終ステータスを知れないため、記録するとステータスの捏造か二重記録になる
- **制御フロー例外（`notFound()` / `redirect()` 等）は API ルートで使わない。** ラッパーはこれを再 throw するためステータスが確定せず記録できない。応答があるのに無記録の経路を作らないよう、**未存在は 404 を明示的に返す**（common-rules のエラー形式に従う）
- **記録できない経路が残る場合は、各リポジトリの `docs/architecture.md` に既知の制約として明記する。** 「記録しているつもりで記録できていない」状態を放置しない

> 実装例は「正準リファレンス実装」を参照。

### fail-open にする

**出力の失敗でリクエストを落とさない。** 監査ログを fail-closed にする考え方もあるが、「ログが出せないとデータが保存できない」方が害が大きい。

- **出力失敗時のフォールバック（`console.error` 等）も落ちうる**ことを前提にする。標準出力が書けない状況では標準エラーも書けない。ここで例外が漏れると**ラッパーの try 内で捕まり、成功済みの応答が 500 に化ける**
- テストは**出力経路が全滅した場合に応答のステータスが変わらないこと**まで固定する。`console.log` だけを壊すテストでは上記を検出できない

### 保持期間と保存先

**標準出力に出すだけでは証跡にならない。** ホスティング先の標準ログは保持期間が短く、「後から調べる」用途には足りないことが多い。**各リポジトリが自分のホスティング先の保持期間を確認し、保存先を決める**。

> 例（2026-10 時点の Vercel）: Runtime Logs の保持期間は Hobby で 1 時間、Pro で 1 日、Enterprise で 3 日。Observability Plus で 30 日窓の中で最大 14 日連続。**これは Vercel の値であり、他のホスティング先には当てはまらない。**

保存先を決める際は、**未認証のクライアントが記録を増やせる経路（未登録パスの 404 等）があること**を前提に流量制御（レート制限・サンプリング）を併せて検討する。これが無いと**本物の痕跡を大量のノイズで埋められる**。


## テスト

- API ルート、および OpenAPI spec を組み立てる箇所は**ユニットテストの作成をもって完了とする**（共通ルール「テストルール」の延長）。
- DB クライアント（Prisma 等）を参照するテストは、実行環境を node にし（例: ファイル先頭に `// @vitest-environment node`）、DB クライアントを `vi.mock` でモックする（実 DB に接続しない）。
- **401 を返す共通ヘルパーのテストで `WWW-Authenticate` ヘッダを固定する。** 401 の生成を 1 箇所のヘルパーに一本化し、ヘッダの検査はそこに置く（各ルートのテストで繰り返さない）。
- **配信 spec の横断的な契約は `paths` を走査する検査で固定する**（**操作の列挙に依存させない**）。列挙にすると操作を足したときの追随漏れが素通りする。走査の起点を誤ると全件パスするため、**検査件数が 0 件ならテストを失敗させる**。
  - 対象: 全操作が 500 を宣言すること、401 を宣言する全操作が `WWW-Authenticate` を宣言すること
  - **失敗メッセージには検査対象を名指しする値を入れる**（`operationId` を持たない spec なら `${method} ${path}`）。常に空になる値を渡すと、落ちても箇所が分からない検査になる
- **エラー応答のボディは「有無」ではなく完全一致で固定する。** 全 4xx / 5xx について、ボディが共通のエラースキーマを指すことを検査する。有無だけを見る検査（`toBeTruthy()` 等）は、**ボディ定義が落ちた応答・別スキーマを指す応答を見逃す**。`$ref` の解決を検査していても参照先が存在すれば通るため、ここは別に固定する必要がある。
- **spec の operation 集合は実ルートから導出する。** spec と手書きの一覧を比べる検査は spec 同士の比較にすぎず、**ルートを足して spec に書かない**と素通りする。`src/app/api/` 等を走査し、**ルートモジュールを動的 import して export を見て**（文字列マッチにしない）、spec の operation 集合と**双方向**に一致させる。実ルートにあって spec に無いものは仕様の欠落、spec にあって実ルートに無いものは spec の嘘。
- **操作ごとに宣言するステータス集合を双方向で固定する。** これは列挙だが、狙いは**ステータスの増減時に表の更新を強制して無言の変更を防ぐ**こと（「実装が返しうるのに宣言していない」の発見は別の手段で行う）。片方向にすると、表の更新を忘れた操作が検査対象から外れて素通りする。操作集合そのものは上記の走査が保証するため、**ファイルシステム → 操作集合 → ステータス集合**の順に根拠がつながる。
  - `operationId` を持たない spec では `"METHOD /path"` をキーにする。
  - **「ある応答が未使用になったら落ちる」類の副作用に頼らない。** 共有 `components/responses` を使う spec では未使用検査が一部を守るが、**複数の操作から参照される応答は 1 箇所消しても素通りする**（実例: 15 操作が参照する 401 を 1 操作から消しても全テスト green だった）。
- 監査ログを出す場合は、以下をテストで固定する。「記録しているつもりで記録できていない」「記録してはいけないものが入っている」はいずれもテストが無いと気づけない。
  - **認証済みリクエストで `userId` が実際に入ること**（認証関数からラッパーまでの受け渡し経路）。受け渡しが壊れると**全テスト green のまま静かに `userId: null` へ退化**し、「誰のキーで」を追う目的を失う
  - **記録されない条件**（登録済みパスへのプリフライト等）
  - **APIキー・リクエストボディが出力に含まれないこと**
  - **出力経路が全滅した場合に応答のステータスが変わらないこと**（fail-open。上記「fail-open にする」参照）
- 全ハンドラがラッパーで包まれていることは**構造テストで固定する**。
  - **包まれているかの判定は、ソースの文字列マッチではなく実体で行う**（ラッパーが返す関数に `Symbol` の印を付け、ルートモジュールを動的 import して印を見る）。文字列で「包まれている形」を探す作りは想定した書き方の列挙になり、列挙漏れが素通りする
  - **検査対象のルートの収集も列挙にしない。** ファイルシステムから導出する。収集側の列挙漏れでも同じく未ラップが素通りする（実例: `route.ts` の完全一致で `route.tsx` を走査対象外にしていた）
    - 拡張子は**フレームワークがルートとして解決する範囲**を網羅する（Next.js の既定は `.ts` / `.tsx` / `.js` / `.jsx`。`pageExtensions` を変えたら検査側も追随させる）
    - 走査の起点ディレクトリを誤ると全件パスするため、**収集結果が 0 件ならテストを失敗させる**

### カバレッジ観点（API ルート）

| ケース | 条件 |
|--------|------|
| 正常系 | 期待するレスポンス・ステータス |
| バリデーションエラー | 不正な入力に対し 400 |
| 認証エラー | 未認証時に 401 |
| 認可エラー（該当時） | 権限不足時に 403 |
| 未存在（該当時） | 対象なしで 404 |
| 競合（該当時） | 重複・競合で 409 |
| サーバーエラー（該当時） | サーバー起因の失敗（DB 障害等）で 500（`{ error }` 形式） |

### カバレッジ観点（Server Actions）

| ケース | 条件 |
|--------|------|
| 正常系 | 期待する戻り値 |
| 未認証 | redirect すること |
| 業務エラー | `{ error }` を返すこと |
| 予期しない例外 | 再送出すること（例外的に `{ error }` に変換する場合は、**サーバー側に記録した上で**返すこと。上記「Server Actions の例外の扱い」参照） |

## 正準リファレンス実装

新規に API 提供を始めるリポジトリは、実装済みの **link-hub** を正準リファレンスとして参照し、そこから複製して着手する。

- リポジトリ: https://github.com/ot-nemoto/link-hub
- 参照ポイント: OpenAPI 配信ルート・API リファレンス UI ルート・spec ビルダー（`info.description` へのナラティブ集約含む）
- ラッパーの包み漏れ検査: `src/app/api/route-wrapping.test.ts`（実体判定の構造テスト）
- 配信 spec と実ルートの対応: `src/app/api/spec-coverage.test.ts`（ファイルシステムから導出し、動的 import した export と双方向に一致させる）。daily-hub / eval-hub にも同一方式で実装済み
- 配信 spec の横断検査: `src/lib/openapi/document.test.ts`（エラーボディの完全一致・操作ごとのステータス集合）
- 監査ログ: `src/lib/audit-log.ts`（ラッパーへの `userId` 受け渡し・レコード生成・出力）、`src/lib/api-response.ts`（ラッパーからの呼び出し）、`src/proxy.ts`（ミドルウェアが応答を返す経路の記録）、`src/proxy.test.ts`（ルート登録漏れの検出）
  - 受け渡しは `WeakMap<Request, string>` で実装している（`Request` インスタンスをキーにする。`AsyncLocalStorage` でも実現できるが、こちらの方が単純でランタイム依存を持たない）
  - daily-hub / eval-hub にも同一方式で実装済み。**3 リポジトリで方式を揃えている**ため、差分が出た場合はどれかが取り残されている可能性を疑う
